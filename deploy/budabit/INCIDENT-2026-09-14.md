## Cause and the verification gap

`PluginEventSifter` maintains a persistent subprocess, launching it on demand
when a write arrives and no running instance exists. It can replace that process
after an error or a plugin command/file change. It does not create a new process
for every event.

The Python process starts its loader asynchronously and immediately serves
JSONL requests. Before discovery, its hosted-community map was empty.
`rules.evaluate` therefore classified the correctly scoped event as ordinary
passthrough. Empty-but-undiscovered and successfully-discovered-empty were not
distinguished. The same event was rejected once the authority view was loaded.

`--status` and `--check-policy` create separate short-lived policy instances,
synchronously load them, report results, and exit. Their success shows that the
database can supply authority; it does not initialize or inspect the actual
ingestion process. A static NIP-11 claim is likewise not readiness evidence.

The earlier signed WebSocket test used an explicit branch configuration rather
than a cold auto-host map. The new regression specifically seeds LMDB, starts
auto-host ingestion, and holds its first discovery scan behind a test-only gate.
It reproduces the failure even after a separate checker has passed.

## Minimal fix and its contract

- Each loader instance starts with `initialized = False`. Only a **complete,
  successful initial load**, including discovery and the branch scans, sets it
  true. A genuinely empty successful discovery is ready; a failed or partial
  load is not.
- With community policy enabled, the live stage accepts **no new writes** until
  its own loader is initialized. Ordinary traffic and authority/bootstrap
  updates temporarily receive `error: relay policy is loading, retry shortly`.
  Known protected-kind deletions keep their permanent rejection message.
  Readiness is a safety condition, not waived by dry-run.
- The request path does not wait on the scanner or queue events. Rejected
  requests do not mutate authority or consume downstream rate-limit tokens.
  Reads remain available; public passthrough and new-community creation resume
  normally after the initial load.
- Failed initial passes retry with 1, 2, 4, 8, 16, then capped 30-second delays
  between attempts, rather than waiting a full ordinary reconcile interval.
  Incoming writes do not trigger extra scans. Waiting is interruptible on stop.
- The initialized flag stays latched during regular reconciliation. Existing
  refresh/inline-update semantics continue, with errors reported in health;
  a refresh error does not itself reset initialization or make known branches
  unhosted. This is not a new atomic-snapshot or global-freshness guarantee.
- `initial_load_complete` is logged once per initialized instance. The stage's
  own health is false while its initial load is incomplete. A separately run
  checker still reports only **its own** instance; do not confuse its output
  with the live process's logs or actual write replies. The completion marker
  also does not prove that every expected branch or permission list exists.

There are no new per-event DB queries or cross-relay fetches. Steady-state cost
is a readiness check; the existing reconciliation interval is unchanged. The
contract is an initialized local authority view, not absolute knowledge of the
latest authority elsewhere. The accepted deletion-replay residual risk is a
separate matter and was not reopened by this fix.

Strfry's lazy process launch is unchanged in this patch. Eager startup could
reduce the first publisher's wait, but is a scheduling improvement, not a
substitute for the readiness barrier on every launch/reload.

## Regression coverage

- All **170 Python tests** passed, including 15 new initialization tests for
  cold writes, partial multi-branch loading, empty successful discovery,
  permanent deletion denials, dry-run, offline fixtures, fresh instances,
  background discovery, capped retries/recovery, ordinary refresh failure,
  and absence of per-event scanning.
- Existing `test/tests/budabitPolicyTest.js` passed: bootstrap, grants,
  moderation, protected deletions, report retractions, and relay restart.
- New `test/tests/budabitStartupTest.js` passed with actual signed localhost
  WebSocket writes and a seeded LMDB, the real background scanner, a successful
  independent health checker, and a deterministic discovery gate. It verifies
  cold rejection, no storage, warm section denials, allowed member/public writes,
  new-community creation, actual plugin mtime reload without a relay restart,
  failed initial scanning, and recovery through the short initial retry loop.
- That same new WebSocket test was run against an isolated copy of deployed
  policy revision `2fc1b38` and failed with the original unwanted acceptance.
  It is included in `test/runTests.sh` so a normal relay suite runs it.

These are source/local-test results, not proof of a fixed VPS deployment.
Publish/build a new reviewed image and perform a separately guarded cutover
before claiming the live cold-start bug is resolved. Do not remove the original
test event or restart the VPS relay merely to demonstrate the race again without
separate authorization.
